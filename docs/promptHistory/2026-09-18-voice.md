## Refined prompt (as executed)

1. **Voice is an input method, not a command path.** The whole phase rests
   on one structural decision: the microphone produces _text_, and that
   text is handed to the existing command interface exactly as if it had
   been typed. There is no voice parser, no voice intent type, and no
   voice execution route. V-004, V-005, V-008 and V-009 then hold by
   construction rather than by a check that can be forgotten, and a static
   audit test asserts the property (no module under the voice feature may
   import a parse, confirm, sign or execute path).
2. **The key never reaches the browser (V-001).** The server mints a
   single-use `realtime_scribe` token from `ELEVENLABS_API_KEY` and returns
   only the token, which expires in fifteen minutes and is consumed on use.
   The browser opens the transcription socket with that token. The API key
   has no path to the client, and a test asserts the route's response body
   carries nothing else.
3. **Push-to-talk, not open mic (V-002, V-007).** The microphone opens on
   an explicit press and closes on release. This is the cheapest correct
   answer to accidental activation: there is no wake word to mis-fire, and
   a press too short to contain speech, or one that yields no committed
   transcript, is discarded rather than submitted.
4. **Live text while speaking (V-003).** Partial transcripts render as
   provisional text and are replaced as the model revises them; committed
   transcripts append. The distinction is visible, so a user can see that
   early words may still change.
5. **Corrections are the user's, not a heuristic's (V-006).** Two kinds are
   handled and kept separate: the model's own revision of a partial
   transcript, and the speaker correcting themselves ("no, make that
   fifty"). The second is detected in a tested pure module and applied to
   the pending text before it is submitted, and the result is always shown
   for review rather than acted on.
6. **Failure falls back to typing (V-010).** Every failure mode the socket
   can report — permission denied, no device, token rejected, quota, a
   dropped connection, silence — resolves to the same place: the text input
   the user already had, with one plain line saying what happened. The
   retry pattern is "I didn't catch that", offered once, and never blocks
   the keyboard.
7. **Confirmation is untouched (V-009).** A voice-originated trade lands on
   the same ticket, with the same review step and the same explicit press,
   as a typed one. Nothing about the voice path shortens it, and the E2E
   proves the trade does not execute until that press.
8. **E2E (V-011)** drives a scripted microphone and socket through a build
   shim, the same mechanism the suite already uses for the authentication
   SDK, and asserts two journeys end to end: a spoken research question
   that returns analysis, and a spoken trade that reaches the ticket and
   executes only after confirmation.
9. Docs: task 069, this file, the roadmap's Phase 12 block, the
   architecture section, the README; lint, typecheck, unit and browser
   suites green; commit and push to the designated branch.

## Why the refined prompt is better

- It converts the two security rows (V-008, V-009) from behaviour that has
  to be remembered into a property of the module graph, and then tests that
  property. A rule that can only be broken by adding an import is a much
  stronger guarantee than a rule enforced at a call site.
- It names where the key lives and what crosses the wire, so "key
  server-side" has a checkable meaning rather than an intention.
- It separates the two things "handle corrections" can mean, which are
  solved by different mechanisms and would otherwise be conflated.
- It makes push-to-talk the answer to accidental activation, rather than
  adding a wake-word detector whose false-positive rate would itself become
  the problem.

## Clarifications assumed

- Push-to-talk only in this phase. No wake word and no always-listening
  mode; both are product decisions with privacy consequences the owner has
  not asked for.
- Audio is streamed to the transcription service and not stored by Mantua.
  No recording is written to disk or to the database; only the resulting
  text enters the command interface, exactly as typed text does.
- The socket is opened from the browser with a short-lived token rather
  than relayed through our server. Relaying would double the latency the
  model's 150 ms design is meant to avoid, and the token already keeps the
  key server-side.
- Voice is offered only where the command interface already accepts text.
  It adds no new command surface and no new capability.
